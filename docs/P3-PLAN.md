# P3 plan (draft for operator approval, 2026-11-03): evidence criteria and verification

Gate (plans/P3-EVIDENCE.md): "Real end-to-end negative and positive scenarios; no fabricated evidence; controlled fulfilment only after all mandatory conditions."
Status: NOT STARTED. Nothing below is implemented. Facts marked (live) were read from the demo site this session; (docs) from Forge/Jira docs.

## Where P1/P2 already stand (so P3 is not re-done)
Done: reviewed-evidence model with PENDING/VALID/INVALID, freshness (expiry, source revision, terms version), separation of duties, independent acknowledgement, reopen/amend with history, audit trail, linked-work observation.
**Real gaps P3 must close:**
1. **"Same customer" is currently self-declared.** The UI copies the contract's own customer reference onto every evidence item, so the wrong-customer check can never fail from the UI, and a reviewer can mark any issue VALID. (PRD J5 needs wrong/untrusted evidence rejected with a clear reason.)
2. **Criteria have a `type` but no checkable meaning.** Nothing verifies that the evidence issue is actually done, resolved, or related to this request.
3. **No decision record.** A FULFIL does not preserve *why* it was allowed (which evidence, which revisions, which checks), so J7 ("why not fulfilled / cite references") and audits cannot reproduce it.
4. **Evidence invalidation after fulfilment is only visible, not recorded** (J6: review-required state with history).
5. **Reviewer authorization is the interim model (ADR-010):** any Jira editor holds every role. PRD roles (support owner, engineering contributor, reviewer, acknowledger, auditor, admin) are not enforced.

## Design
**1. Machine-checkable criteria (pure domain).** A criterion may carry `predicates[]`, each evaluated by the server against facts it reads from the evidence issue AS THE ACTING USER at decision time:
- `STATUS_CATEGORY_IS` (e.g. done), `RESOLUTION_SET`,
- `HAS_LABEL <value>` (e.g. `customer-acme`),
- `LINKED_TO_SOURCE` (the evidence issue has an issue link to this promise's source request; `issuelinks` shape verified (live, docs)).
A criterion is `satisfied` only if the evidence is VALID, current, authorized AND every predicate holds now. New status `unmet` with per-predicate reason codes (e.g. `PREDICATE_FAILED:HAS_LABEL`) so rejection is explainable (J5). No LLM involved; unknown facts => unmet (fail closed).
**Honest limit:** labels and links are set by Jira editors, so they are observable, auditable facts, not cryptographic proof. The control is facts + independent human review + independent acknowledgement, and the report says so.

**2. Customer binding derived, not declared.** `customerReference` on evidence stops being user input. Binding is `HAS_LABEL customer-<normalized ref>` and/or `LINKED_TO_SOURCE`, chosen per criterion. Existing P1/P2 contracts keep working (`predicates` defaults to `[]`; the old self-declared check remains as a secondary guard).

**3. Decision report.** `VERIFY`, `ACKNOWLEDGE` and `FULFIL` attach a bounded `details` snapshot to their audit event: per criterion status, evidence ids, source key/revision observed, predicate results, blockers. Reproducible "why" for J7 and for P5's Rovo read actions. No source content stored (keys, revisions, booleans only).

**4. Review-required after fulfilment (J6).** The view derives `reviewRequired` when a FULFILLED contract no longer satisfies its gates, shown as a banner with reasons. Optional slice: the existing sweep also observes evidence sources (system role, read-only fact `sourceChangedSince`) and sets AT RISK with an audit event. It never reopens or edits anything by itself.

**5. App-level roles (replaces ADR-010).** Role assignments stored per installation (plain KVS), managed only by project administrators (Jira ADMINISTER_PROJECTS checked server-side). Roles: SUPPORT_OWNER (create/confirm/start/deliver/amend request), CONTRIBUTOR (add evidence only), REVIEWER, ACKNOWLEDGER, AUDITOR (read-only), plus APPROVER via Jira admin. Default deny: no assignment => read-only. Domain separation of duties kept. **Operator decision needed:** include this slice (recommended: it makes "authorized reviewer" real) or keep the interim model for the demo and note the limitation.

**6. Evaluation harness (PRD Evaluation).** A deterministic table of synthetic scenarios run through the real domain code: missing deployment, stale test, wrong customer, unrelated issue, duplicate events, contradictory evidence, permitted completion (+ forged/self-reviewed variants). Output: confusion matrix and a `misfulfilment` count (promises fulfilled that should not be), generated by running the code. Nothing hand-written or estimated. Live scenarios (below) are reported separately and labelled as such.

## Slices (each ends green before the next; cut line after slice 3 if time-boxed)
1. Domain: predicates, `unmet` status + reason codes, decision report, tests + mutation checks.
2. Service/adapters/UI: read `labels`, `issuelinks`, `resolution` in the SAME issue read already made (no extra calls), predicate toggles in the create form, human-readable rejection reasons, remove self-declared customer input from the UI, decision details shown in the audit list.
3. Evaluation harness + report file (computed).
4. App-level roles (if approved).
5. Optional: evidence-source observation + review-required banner/AT RISK via the sweep.

## Scopes and manifest
New scopes: **none expected**. The same `GET /rest/api/3/issue/{key}` needs `read:jira-work` (already held); extra fields come in the same call. No new modules, no new entity declarations (predicates live inside the contract document; old documents default to `[]`). `forge lint` will confirm; any change needs your approval.

## Security constraints
Facts always read as the acting user (never asApp) for decisions; predicate kinds are a closed enum validated with Zod, values length/charset-bounded (label values restricted to a safe pattern; never interpolated into JQL); unknown/unreadable facts fail closed; role changes only by verified admins, never from client-declared roles; decision details contain keys/revisions/booleans only; logs codes/counts only; no AI output anywhere near fulfilment (AI is P5, advisory only).
