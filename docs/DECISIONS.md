# Architecture decision log

ADR-001: Forge-hosted TypeScript first, avoiding external infrastructure. Rationale: fewer deployment dependencies and reduced tenant data egress. Validate platform limits before finalizing persistence choice.

ADR-002: Separate engineering delivery from customer fulfillment. Critical invariant.

ADR-003: AI extraction is advisory and needs confirmation. Verification and authorization remain deterministic.

ADR-004: Store minimum necessary evidence metadata; source content remains inside Atlassian wherever possible.

ADR-005: Teamwork Graph and MCP are opt-in enhancements with feature flags, not MVP dependencies.

ADR-006 (2026-11-01, P0, proposed): Spike surface = `jira:issuePanel` (agent view, UI Kit) reading via `requestJira` `.asUser()` with scopes `read:jira-work` + `read:servicedesk-request` (+ `write:jira-work` only when remote-link write is tested). Alternatives: `jiraServiceManagement:portalRequestDetail` (customer-visible; defer, has unlicensed access implications). Evidence: Forge MCP scope lookups, see docs/P0-EVIDENCE.md. Impact: least scopes, user-permission enforcement. Rollback: remove module/scopes, redeploy. Status: implemented and verified live on one synthetic request (ITS-6264, 2026-11-01); the remote-link write and its `write:jira-work` scope were not added.

ADR-007 (2026-11-01, P0): App registration initially blocked by a missing Developer Space; the operator created `promisetwin-dev` and registered the app interactively (`forge create`), then a demo site was provisioned. Personal-app status may need migration to a Developer Space before Marketplace/Codegeist submission — unverified; confirm against Codegeist rules.

ADR-008 (2026-11-01, P0, ACCEPTED by operator for P0 only): Do not hand-patch transitive dependency advisories. `npm audit --omit=dev` shows 9 high (via @forge/react, @forge/bridge, markdown-it, prosemirror-view); latest stable @forge/* gives the same result, so no fix exists from our side. App renders plain UI Kit Text only. Alternatives: pin older versions (npm's suggested 'fix' is a downgrade to @forge/react 11.4.0, not verified safe). Impact: re-check at each phase and before submission. Rollback: n/a. Operator accepted this risk on 2026-11-01 for the P0 spike (no customer data, synthetic demo site, plain-text rendering). Conditions: re-run `npm audit` at every phase gate and before submission; re-evaluate if the app ever renders markdown/ADF or user-supplied rich text.

ADR-009 (2026-11-02, P1, implemented locally): Two counters on a contract. `version` = version of accepted terms (bumps only when criteria are amended; proof and acknowledgement are bound to it). `revision` = optimistic-concurrency counter (bumps on every mutation; compared on write). docs/03-DATA-CONTRACTS.md lists a single `version`; separating them avoids invalidating proof on every edit. Alternatives: single counter (would stale all evidence on any mutation). Rollback: merge counters, migrate stored docs. Not verified live.

ADR-010 (2026-11-02, P1, PROPOSED, interim): Roles come from the acting user's Jira permissions on the issue (EDIT_ISSUES -> AGENT, REVIEWER, ACKNOWLEDGER; ADMINISTER_PROJECTS -> APPROVER), resolved server-side via `mypermissions` as the user. Separation of duties enforced in the domain (no self-review of evidence, owner cannot acknowledge). Alternatives: app-managed role assignments in storage (more correct; needs an admin UI and its own authorization); Jira groups. Limitation: two editors can complete the whole flow. Needs operator decision before P4/P6.

ADR-011 (2026-11-02, P1, implemented locally): Storage = Forge Custom Entity Store (`contract`, `audit-event`), keys `tenant#issue#contract` and `tenant#contract#timestamp#event`, built-in `by-key` index only. Evidence: Forge docs show plain KVS transactions cannot be conditional; entity transactions can (`Filter.equalTo('revision', n)`). Contract + audit event commit in one transaction. Constraints from docs: entity/attribute declarations cannot be deleted after deploy; custom indexes irreversible in staging/production; `query` eventually consistent. Rollback before first deploy: edit manifest. After deploy: not possible for the entities. Live behaviour unverified.

ADR-012 (2026-11-02, P1): Evidence is re-verified at decision time. VERIFY, ACKNOWLEDGE and FULFILL re-read each Jira evidence source as the acting user; missing check = unauthorized, changed `updated` timestamp = stale, unreadable/other source types = fail closed. Source revision is Jira's `updated` timestamp. Limitation: a source edited for unrelated reasons stales the proof (conservative).

ADR-013 (2026-11-02, P1, implemented, create path verified live): Contract creation is idempotent. The client-supplied `requestId` (validated, 8-64 safe chars) is the contract id; a repeat by the same account returns the existing contract, a different account gets VERSION_CONFLICT. Alternatives: server-generated ids (retries duplicate); content hashing (blocks legitimately identical promises). Limitation: a client can choose the id, so ids are not secret; access is still enforced by tenant/issue scoping. Rollback: revert to server uuid.

ADR-014 (2026-11-03, P2, implemented locally): Linked work is an app-owned link stored on the contract (`linkedWork[]`: issue id/key, status category/name, last observed `updated`, linker). No Jira issue-link is written (that needs `write:jira-work` and a Jira-side mutation); it can be added later with explicit approval. Linked work is progress information and is never evidence: the `OBSERVE_LINKED_WORK` command cannot change lifecycle, evidence, acknowledgement or fulfilment, so a Done task never means fulfilled. Rollback: remove the field (defaults to [] on read).

ADR-015 (2026-11-03, P2, implemented locally): Events and recovery. A `trigger` on `avi:jira:updated:issue` (`ignoreSelf`) feeds a sync service; an hourly `scheduledTrigger` and a user "Refresh" use the same service. Observations run as a new `SYSTEM` role that can run exactly one command. Dedupe uses a create-only write (`keyPolicy: FAIL_IF_EXISTS` + 7-day TTL) in plain KVS, so no new entity declarations (entity/attribute declarations are permanent once deployed). The link index (`link#tenant#issue#contractIssue#contract`, plain KVS prefix keys) is an optimization only; the reconciliation sweep enumerates CONTRACTS and self-heals the index (read-first, write only missing rows). Alternatives: poll-only (slower, more invocations), Jira issue properties (needs write scope). Cost risk: the trigger fires for every issue update on the site; the cheap path is one read.

ADR-016 (2026-11-03, P2): Trigger tenant is derived from `context.installContext` (docs: an ARI), not `cloudId`; compared lowercase; unparseable = event ignored (fail closed). VERIFIED live 2026-11-03: a real event applied to a contract (`tenantParsed=true`, `applied=1`), so the derived tenant equals the stored `cloudId` on this site.

ADR-017 (2026-11-03, P2): Sweep bounds and fairness. At most 50 contracts and 50 issue reads per run; the stored resume key advances only past contracts actually processed within the issue budget, so heavy contracts cannot starve later ones; conflicts get one retry then defer to the next sweep. The resume key is a key WE stored (not an opaque Forge cursor, which docs say is unstable).

ADR-018 (2026-11-03, P2): Linked-work visibility is enforced per viewer: links to issues the viewing user cannot read are removed from that viewer's copy (a hidden-count is shown). The stored snapshot is minimal (no summary/description). Role checks run before any Jira read so unauthorized users cannot trigger lookups.

ADR-019 (2026-11-04, P3, implemented locally): Evidence criteria are machine-checkable through a CLOSED set of predicates (`STATUS_CATEGORY_IS`, `RESOLUTION_SET`, `HAS_LABEL`, `CUSTOMER_LABEL`, `LINKED_TO_SOURCE`) evaluated by the server on facts read as the acting user in the same single issue call (no extra Jira requests, no new scopes). Alternatives: free-form expressions or JQL (injection and scope risk), AI judgement of evidence (violates "no AI output bypasses deterministic verification"). Unknown facts fail closed. Honest limit: labels and links are set by Jira editors, so they are observable facts, not cryptographic proof; the control is facts + independent review + independent acknowledgement. Rollback: ignore `predicates` (defaults to []).

ADR-020 (2026-11-04, P3): Customer binding is derived, not declared. Evidence `customerReference` is set server-side from the contract and `CUSTOMER_LABEL` requires the Jira label `customer-<normalized name>` (lowercase letters/digits and dashes; case-sensitive). Previously the UI copied the contract's own customer onto every evidence item, so the wrong-customer check could never fail from the UI.

ADR-021 (2026-11-04, P3): Verification decisions are recorded. VERIFY, ACKNOWLEDGE and FULFILL audit events carry a bounded content-free `report` (statuses, keys, observed revisions, per-predicate booleans) and it is redacted per viewer for evidence issues the viewer cannot read. A FULFILLED promise whose proof stops holding is flagged `reviewRequired` on read; nothing reopens automatically (history is never rewritten). Slice "background evidence-source observation by the sweep" was cut for time and can be added later with the same SYSTEM-role pattern as P2.

ADR-022 (2026-11-04, P3, REPLACES ADR-010): App-level roles. Project admins (Jira ADMINISTER_PROJECTS, checked server-side as the acting user) assign AGENT, CONTRIBUTOR, REVIEWER, ACKNOWLEDGER per project in plain KVS; default is no role (read-only); APPROVER is derived from Jira project admin and is never assignable; SYSTEM never assignable; corrupted or tampered storage cannot grant more than assignable roles. Changes are logged append-only. Admin does NOT imply the other roles. Alternatives: Jira groups (no app-level separation), tenant-wide roles (too coarse). Consequence: after deploy, B and C lose implicit roles until assigned; the live demo needs an assignment step. Rollback: restore the permission-based mapping.

ADR-023 (2026-11-04, P3): The reporting order for a criterion with no satisfying evidence is `conflicting`, then `unmet`, `stale`, `unauthorized`, `missing`: the item closest to success is reported because it is the actionable reason (found by my own scenario test: an old stale item hid the failed predicate). Satisfaction still requires an explicit `satisfied` item and no `conflicting` item.

ADR-024 (2026-11-04, P3, operator-approved after review): Minimum-proof policy. Every REQUIRED criterion of a NEW or AMENDED promise must include the `CUSTOMER_LABEL` and `LINKED_TO_SOURCE` predicates, whatever its type (so the type cannot be used to dodge it); optional criteria are exempt because they never gate fulfilment. Enforced at the service boundary (`clientCreateSchema`, client `AMEND_CRITERIA`); criteria already stored from P1/P2 stay valid and still evaluate as written; the domain stays lenient so old records keep working. Found by the final review (a creator could previously choose "no checks"). Alternatives: leave as is (weaker), per-project policy (more work, later). Not enforced inside the domain's own `createContract`/amend (kept for legacy and tests), so any future entry point must go through the service schemas.

Add one entry per substantive choice with decision date, alternatives, evidence, impact and rollback.

ADR-025 (2026-11-03, P4): Project portfolio authorization and bounds. A new read-only `jira:projectPage` (UI Kit, one page; subpages are Custom UI only) lists promises per project. The project key comes ONLY from Forge context (`extension.project.key`, fail closed if absent; the payload's project is ignored and tested). A promise is listed only if the viewing user can read its SOURCE issue (checked as that user); unreadable ones are counted, never described. Bounds per request: 25 rows, 100 contracts scanned, 50 Jira reads (memoized; reads spent on hidden rows count), resumable opaque cursor validated against the tenant prefix. Rows carry stored facts only (counts of evidence by review state, no evidence keys, no Jira content). `needsMyAction` uses roles ASSIGNED in the project (APPROVER, derived from Jira admin, is not looked up: it needs a per-issue permission call and grants no progress step); it is guidance, the server still re-checks every command. Review-required is derived only for FULFILLED promises; when the read budget is spent the row says `unchecked` instead of guessing. Alternatives: global page (not project scoped), one aggregated JQL query (app-level reads would leak across viewers), a storage index by project (a new permanent entity declaration). Assumption NOT yet verified: `extension.project.key` is present for `jira:projectPage` (documented for the sibling project settings page); the resolver fails closed otherwise and the live run will confirm. Rollback: remove the module and `getPortfolio`; no data or entity changes.

ADR-026 (2026-11-03, P4): One plain-language module for all user-facing codes (`app/src/shared/messages.js` with a `.d.ts`), shared by the issue panel, the portfolio page and the tests; pure, no imports. A test scans the server sources for every refusal code, detail token and audit/command type and fails if one has no text, so a new code cannot ship unexplained (it caught my own new `cursor` token). Unknown detail text is dropped, never echoed. The customer-label rule moved into this module and the server verifier now calls it, so the UI's live label preview cannot drift from enforcement. Deviations from the P4 plan: the timeline has six stages (Acknowledged is its own state in the model) and is built from text and glyphs, not `ProgressTracker` (its stage shape was not in the component reference); loading uses `Spinner` (UI Kit has no Skeleton); the create form is hidden for viewers whose assigned roles lack AGENT (guidance only; the server still refuses). Alternatives: duplicate strings per screen (drift), translate on the server (couples the domain to wording).

## ADR-027 (ACCEPTED by operator 2026-11-04, chat: "Accept, deploy dev"): toolchain gate, stable SDK pins, advisory disposition
- Context: ESLint never parsed TypeScript (P6 evidence); `typescript-eslint` does not support TypeScript 7; `package.json` pinned three prerelease `@forge/*` builds although stable exist; `npm audit` (production only) shows 9 high + 5 moderate, all transitive via Forge SDK packages, with only semver-major downgrades offered as fixes.
- Decision (proposed): (1) TS quality gate = `tsc` strict plus `noUnused*`/`noImplicitReturns`/`noFallthroughCasesInSwitch`/`noImplicitOverride`; ESLint only for the frontend React hooks rule; never report "ESLint clean" for TS. (2) Use stable `@forge/react 12.4.0`, `@forge/bridge 7.2.1`, `@forge/resolver 2.0.2`. (3) Accept the 14 production advisories as inherited and unreachable by our code (reachability not proven), re-check before submission; no semver-major downgrade.
- Supersedes the P0 acceptance in ADR-008 (which covered 9 high + 5 moderate at the time). Consequence: residual risk remains and is disclosed in the submission notes; accepted by the operator on 2026-11-04; re-check advisories before submission.

## ADR-028 (2026-11-05): structured operation logs with a closed field set
- Context: docs/07 asks for structured logs; P0-P4 logged free-form outcome lines. Logs are the one place customer data could leak by accident.
- Decision: every resolver, trigger, scheduled job and Rovo action writes ONE JSON line built by `observability/log.ts` with only `correlationId`, `tenantHash` (8 hex of SHA-256), `eventType`, `result` (code or `error:<Class>`), `durationMs` and numeric counters. No field exists for text, accounts, issue keys or payloads; names and codes must match a strict pattern. `contractId` is deliberately not logged. Remaining free-form `console` lines (two static error messages and one status-code line in the snapshot resolver) contain no user data.
- Consequence: counters named in docs/07 (event_success, policy_denial...) are derived by counting `result` values in logs; no metrics backend exists. Tests assert no sensitive string reaches any log line (8 tests, 6 mutations caught).

## ADR-029 (2026-11-05): parallel Jira reads with a per-request cap
- Context: the issue panel took about 2.2 s because independent Jira reads ran one after another (measured on the dev site).
- Decision: `ContractService` starts independent reads together (issue, permissions, roles; evidence issues; linked issues; audit references) with a cap of 6 concurrent Jira reads per request. A failing permission or role read is rethrown only if the issue is readable, so an unreadable issue is still refused first. Reads stay `asUser` and memoised per request.
- Consequence: median 2233 ms -> 980 ms in a small sample (n=3). Authorization and redaction are unchanged and covered by 9 tests; the cap is a policy number (<= 8) pinned by a test. Portfolio reads are still sequential under a 50-read budget (not changed).

## ADR-030 (2026-11-05): clean-install reproduction on a second Forge environment
- Context: P6 requires a clean-install reproduction; a second Atlassian site was not available.
- Decision (operator choice "Staging env, demo site"): deploy the committed code from a fresh clone to Forge `staging` (v2.0.0) and install it on the demo site, then follow docs/P4-JUDGE-GUIDE.md literally.
- Consequence: proves build, deploy, install, default-deny, fresh storage and the guide's flow on a separate installation; does NOT prove a new site, a new user or Rovo availability elsewhere. The site shows two panels and two agents while both environments are installed. No production deploy; scopes identical to development.

## ADR-031 (2026-11-06): personal-data declaration and the unimplemented reporting obligation (ACCEPTED as option A under the operator's "proceed with the best action"; revisit if time allows)
- Context: the developer console asks "Does your app store personal data?" and the operator answered Yes (the app stores Atlassian account IDs of creators, reviewers, acknowledgers and role holders, with timestamps, in Forge storage; honest answer). Atlassian's user privacy guide says "All apps storing personal data must report user personal data" with the Personal data reporting API (Forge: `privacy.reportPersonalData` from `@forge/api`, 7-day default cycle), and must erase or update data when an account is reported closed or updated. PromiseTwin implements none of this (checked in docs 2026-11-06: developer.atlassian.com/cloud/jira/platform/user-privacy-developer-guide/ and /platform/forge/runtime-reference/privacy-api/). The public privacy text already says there is no delete-a-person function.
- Options: (A) accept the gap for the hackathon, keep the declaration Yes (honest), keep the privacy text as is, and say so in Devpost/limits; (B) implement a minimal reporter inside P7 as a scope exception: scheduled job (weekly) that collects the distinct account IDs from stored promises, roles and audit entries with their oldest `updatedAt`, calls `privacy.reportPersonalData`, and for `closed` accounts removes role assignments and replaces account IDs in promises/audit with a fixed "erased-user" marker (audit stays, person does not), with tests and mutation checks; needs the privacy API's scope/permission requirements verified from docs first; (C) answer No in the console (rejected: inaccurate).
- Recommendation: (B) only if the operator accepts about a day of work and a new production deploy (which would reach installed copies, ADR-027-style risk); otherwise (A) with plain wording. Not decided; nothing implemented.
