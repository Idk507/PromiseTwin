### Whole-machine invariants (measured, seeded and reproducible)
- Setup: 120 seeded runs x 220 steps through the REAL `ContractService`, repositories, link index, inbox and sync (in-memory fakes for storage and Jira). Each step is a user command (right or wrong actor, stale revision, malformed command), a Jira fact change (status, resolution, labels, links, readers, revision) or an event/reconcile run; some commands are replayed with the same event id. Odd seeds give the owner every user role so self-review/self-acknowledge rules are exercised by a user who holds the roles.
- Measured on the last run: **19,049 commands (2,813 applied, 16,071 refused), 1,180 observations of a FULFILLED promise, 839 replays, 1,745 attempts by a user with no role, 0 violations.** The test also asserts these counts are large (so "0 violations" cannot come from an idle run).
- Invariants checked after every step from storage: FULFILLED only with a FULFILL audit event carrying a passing decision report, a GRANTED acknowledgement not given by the owner, and `fulfilledAt`; ACKNOWLEDGED needs the same acknowledgement; no VALID evidence reviewed by whoever added it; lifecycle never skips a forward stage; revision never goes backwards and each applied command consumes exactly one revision; a replayed event id never changes state; a user with no role never changes state; every applied command had an actor holding an allowed role; a refused command never changes the contract; a control contract in another tenant is never altered; every record in the tenant list belongs to that tenant.
- Guard mutations (domain code temporarily weakened, then restored with hash check): FULFILL ignores the verifier, owner may acknowledge, self-review allowed, delivery from any state, a denial advances the lifecycle, revision never bumps: **all caught**. I count that as two layers each redundant for this invariant, not as a gap.

## Slice 4 optimisation: parallel independent Jira reads (LOCAL, committed; NOT yet deployed)
- Cause (from reading the code, then the 2.2 s live median): in `ContractService`, `identify` awaited issue, permissions and role reads one after another; `view` awaited source checks, linked-work visibility, the audit read and the audit redaction in sequence, and each of those looped over issues with one Jira round trip at a time.
- Change (only `app/src/service/contract-service.ts`, no domain, manifest, scope or storage change): (1) `identify` starts the issue, permission and role reads together; a failing permission or role read is captured and rethrown only if the issue is readable, so an unreadable issue is still refused exactly as before; (2) `view` runs source checks, link visibility and the audit read together; (3) per-evidence, per-link and per-audit-ref issue reads run together via `Promise.all` (order preserved); (4) a per-request cap of `MAX_PARALLEL_JIRA_READS = 6` concurrent Jira reads (slots handed over directly) so the speed-up cannot create a burst that trips Jira rate limits. Reads stay memoised per request.
- Tests: `app/tests/parallel-reads.test.ts` (9): reads overlap (max in flight > 1) yet never exceed the cap, each issue read once; same redaction and link order for a viewer who cannot read some issues; audit decision reports stay redacted per viewer (made non-vacuous: the owner sees the hidden issue, the viewer does not); cap holds with 30 concurrent readers; unreadable issue still refused even when its permission read throws (no unhandled rejection); readable issue with failing permission or role read still throws; no-role user still read-only. Suite 485/485 (was 476), `tsc` and `forge lint` clean; the invariant fuzz (19,000 commands) still has 0 violations.
- Guard mutations: cap far too high, slot hand-off bug, permission error beating the unreadable-issue refusal, hidden links not redacted, evidence reads sequential, audit redaction skipped, audit refs treated as readable: all caught. One survivor: link reads made sequential again is not slower in the test data because they overlap with the (longer) evidence reads; I count it as latency-neutral there, not as a gap in correctness.
- Local timing evidence (fake Jira, 15 ms per read, 12 reads): the test requires the list call to finish in < 150 ms where a one-after-another version needs >= 180 ms. This shows overlap, not production speed. **Real speed-up is not yet measured**: it needs a dev deploy and the same page loads as before (previous medians: listContracts 2233 ms, rovo.get_commitment 2503 ms, n = 3 and 1).
